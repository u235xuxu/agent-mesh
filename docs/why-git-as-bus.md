# 为什么用 Git 当消息总线

## 先说结论

因为在目标环境里，**Git 是唯一一个「保证能用」的通道**，而消息队列一个都不保证。

---

## 目标环境的四个约束

这套系统要连的机器，通常长这样：

1. **跨运营商 / 跨地域** —— 一台在本地家宽，一台在海外机房
2. **跨 NAT / 无公网 IP** —— 家里的机器从外面进不来
3. **可能被墙** —— 某些链路对特定协议不友好
4. **可能休眠 / 离线** —— 笔记本合盖就断

在这个前提下，逐个看常见方案：

| 方案 | 为什么在这里不成立 |
|---|---|
| **Redis / RabbitMQ** | 需要一个所有节点都能主动连上的中心。跨 NAT 的机器连不进来，除非做端口映射 —— 家宽通常做不了 |
| **MQTT + Broker** | 同上，且公网 Broker 意味着数据过第三方 |
| **WebSocket 长连** | 笔记本休眠就断，重连状态要自己维护；移动网络下长连耗电且易被掐 |
| **HTTP 轮询** | 需要一台有公网 IP 的服务器做中心点。有 VPS 时可行，但每个节点都要维护一套重试 / 幂等逻辑 |
| **消息队列云服务** | 数据出门，且要付费、要账号 |

**这些方案的共同问题：它们都要求「至少有一个所有节点都能到达的中心」。**

---

## Git 绕开了这个约束

关键在于：**你不需要所有节点互通，只需要每个节点都能到达 Git remote。**

```
A ──┐
    ├──► Git remote (HTTPS/SSH) ◄──┤
B ──┘                             └── C
```

A 和 B 之间可能根本不通，C 可能只能走特定端口，**但只要各自能 push，消息就能流转**。

更妙的是，这台 Git remote 可以是：

- 一台 VPS 上自建的 Gitea / Gogs
- GitHub / GitLab 的私有仓库
- 甚至是一个裸仓库 + SSH

**它顺便解决了另外三件事：**

1. **持久化** —— 消息天然落盘，节点离线多久都不会丢
2. **版本历史** —— 谁在什么时候推了什么，`git log` 一目了然
3. **冲突可见** —— 不像消息队列静默丢弃，冲突会显式报错

---

## 代价是什么

**别只看好处。这个选择有明确的代价：**

### 1. 延迟是秒级，不是毫秒

`git push` + 对端 `git pull`，实际延迟取决于轮询间隔。想要 5 秒内送达，就得每 5 秒 pull 一次 —— **这会让仓库被高频操作拖慢**。

**适合：** 定时同步、异步任务交接、知识沉淀
**不适合：** 实时对话、需要即时响应的协同

### 2. 冲突处理必须自己写

两个人同时改一个文件，Git 会冲突。消息队列不会（它们有分区和顺序保证）。

**应对：** 每个节点只写自己独占的目录，天然不会冲突。见 [isolation.md](isolation.md)。

### 3. 仓库会膨胀

消息越积越多，仓库越来越大，每次 clone 越来越慢。

**应对：** 已读消息定期归档到另一个仓库或直接删除；只保留近期窗口。**这条一定要做，不然半年后 clone 会痛苦。**

### 4. 需要一台常驻的 Git 服务

自建 Gitea 意味着你要维护一个服务。

**应对：** 用 GitHub 私有仓库零维护；或者接受自建的成本换数据自主。

---

## 什么时候该换方案

**如果你的环境满足了下面任意两条，就别用 Git：**

- 所有节点在同一个内网 / 同一个 Docker 网络
- 需要亚秒级消息延迟
- 消息量很大（每天上万条）
- 有稳定公网 IP 且可以做端口映射

**那种情况下，Redis Pub/Sub 或者直接 HTTP + 中心服务更合适。**

**Git 当总线是「恶劣环境」下的最优解，不是「所有环境」的最优解。**

---

## 一个经常被问的问题

> **为什么不用 Git 的 submodule / 分支做隔离，而非要目录隔离？**

因为分支切换会让工作区状态变化，多个 Agent 同时操作一个工作区会互相干扰。**目录隔离 + 服务端 hook 是更简单、更不容易出错的约束方式**，且不需要每个 Agent 理解 Git 分支模型。
